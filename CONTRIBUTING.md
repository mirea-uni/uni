# Правила работы в команде

## Git-стратегия

Мы используем GitHub Flow.

### Ветвление
- `main` — текущая версия
- `docs/[название-через-дефис]` — README, CONTRIBUTING и прочая документация
- `feat/[название-через-дефис]` — новые функции
- `bugfix/[название-через-дефис]` — исправление багов
- `refactor/[название-через-дефис]` — рефакторинг/реструктуризация кода без изменения поведения
- `chore/[название-через-дефис]` — настройка конфигурации, зависимостей и прочее
- `test/[название-через-дефис]` — добавление/исправление только лишь тестов

### Коммиты
Используем [Conventional Commits](https://www.conventionalcommits.org/): `<type>(<scope>): <description>`.
Перечень типов совпадает с типами ветвей выше, за исключением main. Указание scope не является строго обязательным.

- Названия коммитов, а также их сообщения пишутся на английском языке
- Критические изменения необходимо помечать знаком `!`, например `feat(api)!: change response format...`
- Номер таски помещать вниз сообщения:
```
feat(auth): add login endpoint

Refs: UNI-12
```

## Проверки кода

Перед открытием PR все проверки должны проходить:

```bash
uv run ruff check .           # линтер (автоисправление: uv run ruff check --fix .)
uv run ruff format --check .  # форматирование (исправить: uv run ruff format .)
uv run mypy                   # типы
uv run pytest                 # тесты
```

Настройки инструментов хранятся в `pyproject.toml`, версии закреплены в `uv.lock` (`uv sync` устанавливает их).

### Обязательные проверки GitHub Actions

Workflow `Code quality` запускает `Ruff lint`, `Ruff format` и `Mypy` для PR
в `main` и `test`, push в эти ветки и merge queue. Ошибка любой проверки
приводит к падению workflow. Проверки не исправляют код автоматически.

## Code Review

- Каждый MR требует минимум 1 approval от другого участника команды
- Ревьюер проверяет: стиль кода, архитектуру, наличие тестов
- Автор отвечает на все комментарии в MR
